# Setting up a repo for cheap sessions

Every session pays for its entry files on every request, and pays the write price for everything it has to discover. A well-structured repo lets each session load a few short, current files and find everything else with one lookup.

These are the pieces used in the repo this skill came from, with why each one saves tokens. Adapt the templates in `templates/` and add only what the project needs.

## 1. A short entry file

`AGENTS.md` (from `templates/AGENTS.template.md`) holds the standing directives, the session protocol, the token rules, a doc map and the definition of done, and nothing else. `CLAUDE.md` (from `templates/CLAUDE.template.md`) is the line `@AGENTS.md` plus Claude Code specifics, so every agent reads the same source. The clear-or-keep maths stays out of the entry file, in `CHECKPOINTS.md` (section 11).

Keep the entry file short: every request of every session carries it. Aim for under ~200 lines; move specialized workflows (PR reviews, migrations) into skills that load on demand. Measure it: `/context` shows the entry file and tool definitions, and 5k tokens of entry file costs about $0.10 per 100-request WP. `lint_context.py` (section 14) fails CI when the budget is exceeded.

Add a six-line command sheet (build, one test, lint one file, run, regenerate the map) to the entry file or a `docs/COMMANDS.md` it points at. It costs ~60 tokens per request and saves a discovery round trip plus a doc read.

## 2. A handoff file

`STATUS.md` (from `templates/STATUS.template.md`) stays at 40 lines or fewer. It records:
- the current milestone, the next task and the last one done
- **Start here**: exactly which docs the next session loads, and nothing more
- open questions for the owner
- environment notes that a fresh session would otherwise have to rediscover
- a session log of at most five entries, newest first

It is rewritten at every checkpoint. It is what makes `/clear` safe and cheap.

## 3. A roadmap read one section at a time

`ROADMAP.md` (from `templates/ROADMAP.template.md`) has one `## M<n>` section per milestone. Each work package is sized for one session, with a size, its dependencies and acceptance criteria.

- Detail only the next milestones. Refine later ones just in time; the first task of each milestone refines its packages.
- Agents read only the current section: `grep -n '^## M' docs/ROADMAP.md`, then a line range.
- Split a package that outgrows its session.
- Size a WP in requests, not lines (S≈20, M≈50, L≈100). Record the estimate in ROADMAP and the actual in COST.md; a WP that consistently takes 2× its estimate should be split.
- Keep a `## Later` list for opportunistic work. "While I'm here" is a full-context round trip; capture it in one line and continue.

## 4. A decision index

`DECISIONS.md` (from `templates/DECISIONS.template.md`) is a table with one row per decision and the alternatives considered, plus open options that each carry a recommended default.

- Agents read the tables and open an entry only if their task touches it.
- A decision is recorded once and never reopened without the owner, so nobody re-litigates it.
- Record looked-up facts here too, such as prices, with their date and source.

## 5. A doc map

A table in the entry file maps each need to the doc that covers it. Agents go straight to one doc instead of listing directories.

## 6. Contracts and a generated code map

- Each module or crate starts with a contract comment covering its purpose, a public API summary, invariants, dependencies and how to test it. Its first line is a one-line summary.
- `docs/MAP.md` lists every file with its approximate size, a token estimate for large files, and that summary; Markdown entries also list their `##` sections with line numbers, so reading one section is a single call. It is generated by `scripts/gen_map.py` in this skill, and CI checks that it is fresh with `gen_map.py --check --out docs/MAP.md` (or `lint_context.py`, section 14).
- Agents locate code from the map, read the contract, and read the implementation last, by line range.

## 7. Files that stay cheap to read

- Keep source files to about 400 lines or fewer, one concept per file. No `utils` grab-bags.
- Make code searchable: unique identifiers and stable error strings, domain-prefixed names, no `utils`/`helpers`/`common`, no barrel file that hides locations. `git grep` should return one hit.
- Make failures self-explaining: a failing check prints the file:line and the likely fix or doc link. An error message is documentation read only when it fires.
- Extend through data: presets, patterns, rules and collectors are one small file each, so an addition touches one file.
- Write docs breadth-first: the first five lines answer the question and the rest is detail, so a short read is enough.
- Write down a feature recipe (the steps and file locations for a typical change) so agents don't explore to find the pattern.

## 8. Quiet tooling

- Provide one `check` command that runs everything CI gates on and prints only a summary and the failures.
- Bound tool output at the source: `MAX_MCP_OUTPUT_TOKENS` (default 25,000) and `BASH_MAX_OUTPUT_LENGTH` (default 30,000 characters). Lower them to your worst useful log; redirect huge logs to a file and grep it.
- Configure test runners for failures-only output, or filter with a `PreToolUse` hook so bulky output never enters context (see `reading-playbook.md`).
- List the files agents must not read in the entry file: lockfiles, generated code, build output, data, snapshots.
- Optionally enforce that list with Claude Code permission rules, for example `"permissions": {"deny": ["Read(./Cargo.lock)", "Read(./target/**)"]}` in `.claude/settings.json`.
- Enforce the read guard: copy `scripts/guard_read.py` to `.claude/hooks/` and start from `templates/settings.template.json`. It denies a whole-file read above ~600 lines and asks for a range, so the rule costs nothing until it fires. A `SessionStart` hook can also run `start.py` and inject the reload when the client supports `additionalContext`; skip it when sessions are not all WPs.

## 9. Durable state

- Commit every significant change, push, and keep CI green. Git plus `STATUS.md` is what lets a session end at any checkpoint.
- Update docs in the same commit as the change that would make them stale. Stale docs cost tokens later, because the next session has to re-derive the truth.
- For independent large WPs, run two sessions in separate worktrees. Each pays its own fixed overhead (~20k tokens), so it wins only when both are 50+ requests and neither would otherwise wait on the other. Don't switch branches inside a live session.

## 10. Checkpoints in the session protocol

The protocol has four steps:
1. **Start:** run `scripts/start.py` (section 12): it prints `STATUS.md`, the current roadmap section and the doc map in one call.
2. **Locate:** use the code map and contracts.
3. **Work:** one package at a time, with tests alongside the code.
4. **Finish:** run check → tick the roadmap → rewrite `STATUS.md` → append the WP row to `docs/COST.md` (section 13) → commit → push → wait for green CI → make the clear-or-keep checkpoint decision (see section 11).

During work, run the ladder: touched file → targeted test → one full `check` at the finish. Order `check` fastest-first and stop at the first failure; a retry or a second full run is another full-context request.

## 11. An on-demand checkpoints doc

`CHECKPOINTS.md` (from `templates/CHECKPOINTS.template.md`) holds the cost model and the clear-or-keep test that the entry file only points at. It is read at a checkpoint, not on every request, so the entry file stays short while the maths stays exact. The doc map in the entry file has a row for it. Measure R with `clear_or_keep.py --measure docs/STATUS.md docs/ROADMAP.md:M<n>` rather than estimating it: a measured reload is what makes the template's thresholds meaningful.

## 12. One call to re-orient

`scripts/start.py` (copy it into the repo from the skill) prints `docs/STATUS.md`, the `## M<n>` section named by its milestone, and the entry file's doc-map rows in one tool call. That is the reload after a clear: one request instead of three, and it cannot drift from the files' format.

```bash
python3 scripts/start.py
python3 scripts/start.py --status docs/STATUS.md --roadmap docs/ROADMAP.md --entry AGENTS.md
```

Keep its output under ~120 lines. A large reload makes every clear expensive (section 11).

## 13. A cost ledger

`docs/COST.md` (from `templates/COST.template.md`) gets one row per WP at the checkpoint: date, requests, prompt tokens, cached share, output, dollars and the clear-or-keep decision. It is measurement, not documentation.

- Fill it from `/usage` (or a statusline) at the checkpoint; prompt tokens are `input + cache_creation + cache_read`.
- Track cost per completed WP, not per session. A WP at twice the median is a leak: stale map, grown entry file, or rework.
- Keep the last ~20 rows and archive the rest.
- Give each WP a dollar budget. Exceeding it usually means the WP is too big; split it next time.
- Run `scripts/cost_report.py --path docs/COST.md` at each checkpoint: median, p75, trend and outliers. Add `--max-median` in CI as a budget.

## 14. A context lint in CI

`scripts/lint_context.py` (copy it and `gen_map.py` from the skill) checks the invariants in this doc and prints only problems:

```bash
python3 scripts/lint_context.py --root . --strict
```

It fails when the entry file plus its imports exceed ~5k tokens, `STATUS.md` exceeds 40 lines, a doc over 300 lines has fewer than three `##` sections, any `##` section exceeds 120 lines, a backticked path or local link in any doc is dead, `@` imports nest, or `docs/MAP.md` is stale. It warns on prose copied between docs; `--strict` makes those failures too. Run it in the same CI job as the tests; it needs no dependencies.

## 15. Generate, don't author

For repeated changes — a new endpoint, migration, fixture, or a rename across many files — keep a generator or codemod in the repo. The model runs one command and reviews the diff instead of writing the files out: a 2k-token file costs 5× and is typo-prone; the command costs a few dozen tokens. Give the generator a `--dry-run` and make its output quiet.

## Auditing an existing repo

Report findings as a short table with one row per item: the item, what you found, the fix, and a rough token impact. Check:

- Is the always-loaded entry file short? What does it add to every request?
- Is the clear-or-keep maths in an on-demand doc (the doc map points to it), not in the entry file?
- Is there a handoff file that names exactly what to load next?
- Can the roadmap and specs be read one section at a time?
- Can agents find decisions without reading history?
- Is there a code map, and do modules start with contracts?
- Are there files over ~400 lines that agents read often?
- Do failures name the fix, or send the agent exploring?
- Are there `utils`/`helpers`/barrels that make grep noisy?
- Are enforceable rules in hooks/permissions, or only in prose?
- Is there a verification ladder, or a full suite after every edit?
- Does `check` print a summary, or pages of logs?
- Are bulky and generated files listed as off-limits?
- Is state committed often enough that a clear is always safe?

### Session audit

From `/usage` and a skim of one transcript, look for the leaks a repo check cannot see:

| Leak | Typical cost |
|---|---|
| 10k of unused tool definitions or plugin tools | ~$0.20 per 100-request WP |
| A 2k-line file read to find one function | ~25k tokens written, then carried by every request |
| Eight sequential lookups instead of two | ~$0.18 at 150k of context |
| A stale map causing directory exploration | 20–60k tokens written |
| `STATUS.md` at 120 lines | adds to R on every clear |
| Rework after a wrong plan | the whole exploration, twice |

- Audit one transcript with `scripts/audit_transcript.py session.jsonl`: requests, cache split, top files, re-reads, largest turn and estimated cost.
- Which files were read that the task never touched? Any whole-file reads of large files?
- How many round trips did one lookup take? Could it have been one command?
- Did the agent re-read anything it had already seen or written?
- Did it explore because the map was stale or a doc had no sections?
- How big was the reload at the last clear? A large handoff makes every clear expensive.
- Did `/usage` name a prefix breaker? Each miss re-writes everything after it.
- Did the session stop at green, or keep polishing after it?
